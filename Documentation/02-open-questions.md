# Open Questions

- ❓ **Apple Silicon vs Intel Mac.** Drives URSim emulation cost and `ur_rtde` wheel availability. *Confirm.*
- ❓ **`ur_rtde` arm64 macOS wheel** for the chosen Python. **RESOLVED 2026-06-16:** `ur_rtde` 1.6.3 (latest) ships **no macOS wheels** — only manylinux (Linux) + win_amd64. Source build is the **only** path on Mac (not a fallback). Hard build deps: `cmake`, `boost`, Xcode Command Line Tools. **Pin Python 3.12** — `ur_rtde` ships/tests ≤ cp312; Python 3.14 is untested and fails the build (the dev Mac defaulted to Homebrew `python@3.14`, which caused the first failure). Clean setup must also pin the Boost version, since the Mac build links against system Boost.
- **Build attempt 2 (2026-06-16):** Python 3.12 + cmake fixed the earlier errors, but Homebrew **Boost 1.90** breaks `ur_rtde` 1.6.3's CMake — config-mode `BoostConfig.cmake` can't resolve the `boost_system` component (header-only in modern Boost). Workaround under test: force legacy module-mode Boost lookup via a `CMAKE_TOOLCHAIN_FILE` env shim (`Boost_NO_BOOST_CMAKE=ON`, `CMP0167=OLD`); `ur_rtde`'s `setup.py` passes env through to cmake, so no patching needed. (Caveat: module-mode `FindBoost` is deprecated in CMake 4.x.)
- **Robust fallback / open decision:** if the native macOS build stays fragile, run the **comms layer in Linux (Docker)** where `ur_rtde` installs as a prebuilt manylinux wheel (zero compilation) — also a more reproducible base for handoff. **Fork to decide: native macOS build vs. containerized comms.**
